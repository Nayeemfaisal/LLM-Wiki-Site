Practical workflowUpdated 28 October 2026

What can a battery researcher do with this work?

The wiki is a decision tool. It helps a researcher decide whether battery files are suitable for a time-series, EIS, and DRT study before claiming that measurements or model results are comparable.

Two user cases, one rule: the workflow does not invent links between files. It accepts a match only when the cell, state, temperature, protocol, units, and timing evidence support the intended comparison.
User case 1

Screen a new battery dataset before spending time on modelling

User: a researcher has a new archive containing cycling CSV files and perhaps EIS files. They want to know whether it can support a TS-EIS-DRT study.

Input

What the researcher provides

  • Data files and available documentation.
  • Cell identifiers, chemistry, temperature, cycling protocol, and units where available.
  • The intended outcome: for example SoC, SoH, EIS comparison, or DRT analysis.
Checks

What the workflow checks

  • Are time-series and EIS measurements present?
  • Can records be linked to the same cell and condition?
  • Are units, timestamps, and protocol fields usable?
  • Does the EIS input pass structural and quality screening before DRT?
Output

What the researcher receives

  • A source manifest and availability summary.
  • A decision: usable, usable with restrictions, or not suitable yet.
  • A short list of missing metadata or checks required before modelling.

Example decision

Candidate archive: it contains cycling curves and EIS spectra from the same battery type, but no common cell identifier or state-of-charge record.

Result: it can support separate TS and EIS exploration, but it cannot yet support a matched TS-to-EIS or DRT claim. The next action is to recover the missing test log or restrict the work to a documented subset.

User case 2

Prepare a small matched set for DRT and comparison

User: a researcher has selected measurements from the same cells and wants to compare an EIS-derived DRT representation with the battery's preceding or nearby time-series behaviour.

Input

What the researcher provides

  • A fixed list of cells and measurement identifiers.
  • TS windows and EIS spectra with known test conditions.
  • A predeclared matching rule, such as same cell, temperature, state range, and cycle window.
Method

What the workflow does

  • Freezes the match manifest before modelling.
  • Runs EIS quality metadata checks.
  • Runs DRT reconstruction with saved settings and stability/uncertainty checks.
  • Compares any learned result with a simple held-out baseline.
Output

What the researcher receives

  • A traceable matched dataset for analysis.
  • Plots and result tables with the link back to the source measurements.
  • A conclusion of support, partial support, no support, or inconclusive.

Example decision

Matched subset: EIS spectra and pulse/cycling records are available for the same CALB cells at recorded temperatures and protocols.

Result: the subset becomes an internal evidence package for a controlled comparison. It is useful for testing the workflow, but it does not justify a universal model claim until it succeeds on an independent matched set.

How to use this wiki

Start with the question you need to answer

  1. "Can I use this dataset?" Start at Dataset targets, then use the source and screening pages.
  2. "Can I claim the measurements are matched?" Review the matching rules and external-validation limits before joining records.
  3. "Can I run DRT?" Check EIS quality first, then use the DRT route with saved settings and uncertainty/stability evidence.
  4. "Does the model transfer?" Use the recorded comparison against simple baselines. A small improvement or a failed result is still useful evidence.
Research boundary

What this does not do yet

The current work does not offer a universal battery-health prediction service. It provides a reproducible route for selecting defensible data, preparing quality-checked EIS for DRT, and deciding when a model result is scientifically supported.
